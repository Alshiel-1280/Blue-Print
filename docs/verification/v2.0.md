# v2.0 implementation verification

## Automated acceptance

The v2 test suite covers:

- v1 root sentinel remains byte-for-byte unchanged during v2 setup;
- schema 1 contains no `payload_json`;
- normalized bookkeeping, evidence, billing, settlement, closing, and audit
  persistence;
- invoice draft issue as a generated PDF plus posted receivable/revenue journal,
  followed by idempotent full settlement and a posted receipt journal;
- persistent job idempotency and recovery after reopening;
- evidence OCR candidate storage and duplicate-original rejection;
- idempotent CSV import, duplicate isolation, rule-candidate generation, and
  explicit evidence-match acceptance;
- recurring and import-rule candidate generation without automatic posting;
- explicit candidate confirmation;
- encrypted repair backup before transactional repair;
- v2 backup round trip and rejection of v1 families;
- staged restore while preserving the prior v2 root;
- `.bprules` signature, hash, key, revision, year, and support-scope checks;
- independent invoice-date, taxable-period, registration, tax-rate, and cap
  boundaries;
- Argon2id vectors, wrong password, tampering, corruption, and KDF limits;
- signed manual update manifests;
- durable, idempotent XTX generation, failed validation persistence, annual
  support rejection, and deterministic recreation of a missing output file.

Run:

```sh
swift test --parallel
swift build -c release --product BluePrint
swift format lint --recursive --strict Sources Tests Package.swift
git diff --check
```

## Local package inspection

Build an ad-hoc QA package with:

```sh
BLUEPRINT_SWIFT_DISABLE_SANDBOX=1 \
  ./scripts/package-app.sh release /tmp/blueprint-v2-app self
codesign --verify --deep --strict --verbose=2 \
  /tmp/blueprint-v2-app/BluePrint.app
codesign -d --entitlements :- \
  /tmp/blueprint-v2-app/BluePrint.app
```

Confirm the App Sandbox, user-selected read/write, and outbound network client
entitlements, arm64 executable, v2 version metadata, and bundled `.bprules`
resources.

## Manual UI audit

The release candidate must be inspected using an isolated sample v2 database,
without reading or mutating a v1 root. Audit these ten scenarios:

1. first-run setup and unsupported-year messaging;
2. Home empty state and next action;
3. manual journal creation;
4. evidence import and OCR failure/success;
5. template, recurring schedule, and rule candidates;
6. explicit single and bulk candidate confirmation;
7. Books, ledger, and trial-balance keyboard flow;
8. Closing blocker and decision flow;
9. Filing support matrix, including disabled 2026 output;
10. backup, staged restore, diagnostics, repair preview, and failed-job state.

For each, verify keyboard access, VoiceOver labels and hints, empty state,
failure state, resumption state, focus order, clipping, and contrast. Store
screenshots and findings with the release evidence.

## Official release gate

Run `scripts/release-preflight.sh` and `scripts/release-app.sh` with the official
Developer ID identity, Notary Service Keychain profile, and HTTPS release URL.
The gate requires:

- all tests and Release build;
- Hardened Runtime and v2 App Sandbox entitlements;
- signed app and signed DMG container;
- successful notarization and DMG staple validation;
- Gatekeeper success for the DMG and contained app;
- published SHA-256 and signed update manifest;
- successful launch on a clean, separate Apple Silicon Mac.

The official notarization, clean-Mac launch, and ten-scenario audit are
release-operator evidence and must not be inferred from unit tests.
